# 算法详解

本文档拆解 Xinxin 里四个「不显然」的机制：技能路由（三通道检索 → 融合 → 扩展 → 重排 → 分流）、
证据门控的 Shared LinUCB、任务引擎的预算与续接、以及提示空间压缩策略。
全部参数均可在代码中对照：`backend/app/skills.py`、`backend/app/skillnet/`、`backend/app/agent.py`。

## 1. 技能路由：从 1800+ 技能里挑出「必要的几个」

大多数 Agent 把全部工具定义塞进系统提示——技能一多上下文就爆炸；或者只做向量 Top-K，
容易把「同领域但本轮没用」的技能带进来。Xinxin 把问题拆成两步：
**先缩小空间**（多通道召回 + 融合 + 图扩展），**再判断必要性**（LLM 重排，允许弃权），
最后按置信度决定执行姿态。

### 1.1 总流程

```
任务文本
 ├─ 通道 A：BM25 词汇召回            top-20
 ├─ 通道 B：E5 稠密语义召回          top-20   （无模型时降级为词法向量）
 └─ 通道 C：领域 / 标签结构召回      top-20
        │
        ▼  weighted_fuse：每路 min-max 归一化 → 加权求和 → 多路命中加成
   融合候选（bm25 0.35 / dense 0.55 / structural 0.10）
        │
        ▼  质量先验：score × (0.85 + 0.3 × quality)，quality 缺省 0.6
        ▼  学习加成：+ 0.1 × LinUCB 优先级（仅当已有学习更新时）
        │
        ▼  关系图扩展：compose_with × 0.88 / depend_on × 0.80
   扩展候选
        │
        ▼  LLM 任务必要性重排（一次模型调用；可少选、可不选，给出理由）
   最终选择
        │
        ▼  置信度分流（按 BM25 原始分，跨查询可比）：
       ≥15 自动执行 · [2,15) 先确认 · <2 不选技能直接答
        │
        ▼  依赖拓扑排序 → 只把选中的技能卡注入系统提示
```

三档模式由 `XINXIN_SKILLNET_MODE` 控制：`bm25`（纯基线）、`hybrid`（到质量先验为止）、
`fabric`（完整链路，Agent 默认）。

### 1.2 通道 A：BM25 Okapi

标准 Okapi BM25，`k1 = 1.5`、`b = 0.75`：

```
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
score(d,q) = Σ_t idf(t) · f(t,d)·(k1+1) / (f(t,d) + k1·(1 - b + b·|d|/avgdl))
```

分词是中英混合的：英文按词（`[a-zA-Z][a-zA-Z0-9_-]*`），中文按 1-gram + 2-gram，
带中英停用词表。选 BM25 而不是纯向量的原因：**BM25 原始分跨查询可比**——
同一个词频分布在不同查询下分数尺度一致，因此它被选作置信度分流的标尺
（融合分是不可比的，不能用来定阈值）。

### 1.3 通道 B：E5 稠密语义（int8 ONNX）

- 模型：E5 系稠密编码器，int8 量化 ONNX，384 维，`onnxruntime` CPUExecutionProvider，
  2 线程；权重与 `manifest.json`（字节数 + SHA-256）一起分发，**启动时校验完整性**，
  请求路径上不发生任何下载
- 编码：mean pooling + L2 归一化；查询加 `query: ` 前缀、文档加 `passage: ` 前缀；
  截断 256 token
- 缓存：技能向量按「模型 revision + ids + texts」的 SHA-256 命名存 npz，
  复用前校验形状、dtype、有限性与归一性，脏缓存直接重算
- 降级：`XINXIN_SKILL_ENCODER=auto`（默认）在模型或推理不可用时切到词法向量
  （2048 维 hashing TF-IDF + 余弦）；`dense` 模式则 fail-fast

词法降级通路也认真做过工程细节：哈希用 `zlib.crc32` 而不是内置 `hash()`——
后者受 `PYTHONHASHSEED` 影响，跨进程不可比，索引无法持久化、历史结果无法复现。

### 1.4 通道 C：结构召回

按领域与标签匹配：命中一个长度 ≥2 的标签加 0.3。权重最低（0.10），
作用是「同领域兜底」——当词汇和语义都没把握时，至少不跑偏。

### 1.5 融合：加权分数融合 + 多路一致加成

每路先做 min-max 归一化，再加权求和：

```
fused(d) = Σ_c w_c · (s_c(d) - lo_c) / (hi_c - lo_c)     （span=0 时：s>0 记 1，否则 0）
fused(d) += 0.05 × (命中通道数 - 1)                        （一致加成）
```

两个针对上游的修正：

- **平分正分通路也要给分**：上游 `(s - lo) / 1` 在整路同分（例如多个技能同领域）时
  会把所有命中抹成 0；这里 span=0 且 s>0 时记 1.0
- **一致加成**：被多路同时召回的技能额外加分，防止单路噪声项挤掉真实目标

权重：稠密编码器可用时 `(0.35, 0.55, 0.10)`（语义主导），词法降级时 `(0.70, 0.20, 0.10)`
（词汇回归主导）。

### 1.6 质量先验与学习加成

```
score' = score × (0.85 + 0.3 × quality)      quality 缺省 0.6
score'' = score' + 0.1 × linucb_priority     仅当 n_updates > 0
```

质量先验让同等相关的技能里评级高的略占优；学习加成被刻意压到 0.1 的弱权重——
检索的「相关」由本轮的查询决定，「历史上好用」只是微调。

### 1.7 关系图扩展

技能之间有 `compose_with`（协作）与 `depend_on`（依赖）两种边。
融合榜上的每个技能，把邻居以 `score × 0.88` / `score × 0.80` 注入候选。
这让「你选了 A，B 常和 A 一起用」的知识可以进入候选，但**不进入最终提示**——
是否真的需要，仍由 LLM 重排决定。

### 1.8 LLM 必要性重排

一次模型调用，输入任务文本与候选技能卡，输出：选中集合 + 每个的理由 + 是否弃权。
**允许明确返回空**——「这些技能都不需要，直接用通用能力答」是一个合法输出。
没有密钥、调用失败、或 `max_calls < 2`（一次重排 + 至少一次执行）时自动降级，
不中断任务。审计字段（`candidates` / `graph_added`）只用于界面展示，不进系统提示。

### 1.9 置信度分流

标尺是 BM25 原始分的最高分（跨查询可比）：

| BM25 原始分 | 姿态 | 含义 |
| --- | --- | --- |
| ≥ 15 | auto | 匹配明确，直接执行 |
| [2, 15) | confirm | 大致相关，把技能卡给模型但提示其谨慎 |
| < 2 | direct | 不选技能，通用直答（只给建议，不硬过滤） |

`confidence = min(1, raw_top / 15)`，字段名刻意写成 `confidence_kind:
heuristic_relevance_not_probability`——它是相关度的启发式，不是校准过的概率。

## 2. Shared LinUCB：证据门控的策略学习

技能「被选中」不等于「有用」。Xinxin 只有同时满足两个条件才允许学习：

1. 本轮 `skills` 事件里确实选中了该技能；
2. 事件流里有 `tool.completed` 且 `ok = true`，且该工具属于这个技能。

满足才受理 `POST /api/v1/skills/feedback`；同一 `run_id + skill` 有 marker 防重复提交。
这避免了「模型说它好 → 排得更前 → 更常被选中」的自我强化。

### 2.1 模型形态

共享参数（shared/disjoint 的反面）LinUCB：

```
优先级(task, skill) = θᵀφ(task, skill) + α·√(φᵀA⁻¹φ)
θ = A⁻¹b        A ← A + φφᵀ        b ← b + r·φ
α = 0.25        （r 为人工反馈奖励）
```

- 全局只有一份 `A`、`b`：所有历史观测共同拟合 θ，天然跨技能泛化
- 第二项是探索奖励：某个方向被观测得越少，不确定性越大、加分越多
- 状态持久化在 `settings` 表的 `skill-policy` 键，重启不丢

### 2.2 上下文特征 φ（152 维）

| 段 | 维度 | 内容 |
| --- | --- | --- |
| task 词袋 | 64 | IDF 加权 hashing（CRC32） |
| skill 词袋 | 64 | 同上，各自编码 |
| 领域 | — | 任务与技能领域重合度 |
| 交互 | — | 标签交集占比 |
| 元特征 | — | 质量、流行度等标量 |

维度是调出来的：早期 24 维时中文文本经 hashing 后碰撞严重（51 个技能就分不开），
升到 64 维后检索与学习都稳定。哈希一律 CRC32，理由同 1.3——跨进程可复现。

## 3. 任务引擎：有状态的执行单元

一次提交不是一次请求，而是一条持久化的执行记录：

```
POST /runs {task, permission, max_calls, max_seconds, request_key}
   → runs 表落一条（request_key 唯一 → 重复提交返回同一 run_id）
   → 单 worker 取队：started
   → SkillRouter.search → skills 事件
   → build_system_prompt → ModelGateway 流式
   → 工具调用 → tool.started / tool.completed（ok + 结果摘要）
   → 每步事件写 SQLite 并 SSE 推送
   → finished：result / error / usage 一起落库
```

### 3.1 预算与姿态

三层预算同时生效：模型调用次数 `max_calls`、累计令牌 `max_total_tokens`、
墙钟时长 `max_seconds`。耗尽即停，状态为 failed 并写清原因
（「本轮累计令牌达到预算（x/y）」），**已执行的工具记录全部保留**，
不清空现场——因为下一轮续接要用。

### 3.2 续接（resume）

`POST /runs/{id}/continue` 开一条 `resume_of` 指向原任务的新 run。
系统提示不依赖模型记忆，而是把上一轮的工具证据（带 `seq`、参数、结果摘要）
重新注入，并重建工作摘要。停机期间不补跑定时任务，避免副作用堆积。

### 3.3 取消与进程树

取消是协作式的：worker 与子进程都观察同一个 `cancelled` 事件。
Windows 上子进程以 `CREATE_SUSPENDED` 启动，随即由 WindowsJob 收编进作业对象——
作业句柄关闭（进程退出）时整棵树被内核终止，不会留下孤儿进程。

## 4. 提示空间压缩策略

系统提示有预算，超限时按固定顺序压缩，**先丢信息量小的**：

```
1. 记忆         → 只留最近少量条目
2. 技能卡       → 压成 selected_ids（保留 id，丢正文）
3. 前轮工具证据 → 裁剪条数与摘要长度
4. 长文本       → 截断
```

这条顺序是修出来的：早期版本先裁工具证据，导致续接任务丢掉上一轮的执行记录，
测试直接失败。现在候选技能的审计数据（`candidates` / `graph_added`）明确排除在提示外，
只走界面展示通道。

## 5. 与之相关的其他算法细节

- **上传幂等**：`X-Upload-ID` + `uploads` 表签名比对，网络抖动重试不会落两份文件；
  落盘本身是 staging 目录 + 原子 rename
- **登录限流**：scrypt 哈希 + 8 次/15 分钟的失败锁定，按账号维度
- **SSE 重连**：客户端带 `Last-Event-ID` 游标；单条坏事件跳过不中断流
  （截断的 JSON、网关注入的杂项都不该让任务流死掉）
- **Vite Host 校验**：隧道域名访问静态页 403 而 API 正常的经典问题，
  解法是 `allowedHosts` 放行隧道域名族，见 `frontend/vite.config.ts` 注释
