# zhishi 与 Xinxin 出题链路比较

参考源码：本机只读 `集成项目/sources/zhishi`，提交 `0084bf1a1601b914b8c33edc04278033d93a7da9`；[上游仓库](https://github.com/wangchuri/zhishi/tree/0084bf1a1601b914b8c33edc04278033d93a7da9)。Xinxin 问题基线为 `64eb7b0`。以下区分源码结论与真实资料诊断，不将上游实现等同于质量保证。

| 环节 | zhishi 源码 | Xinxin 基线与教训 |
| --- | --- | --- |
| PDF 理解 | `services/parser.py` 检测扫描件、数学字体、Type3 字体与密集矢量，必要时交 MinerU 处理公式和版式 | 普通文字 OCR 能读汉字但不能保住分式和上下标。识别到足够字数不等于完整理解；实测失败书有大量低置信度页面 |
| 上下文 | `agents/question_gen_agent.py` 每页独立上下文，`get_near_page` 按需补页 | 4000 字片段可能横跨十多页；错误 OCR 把许多残缺题拼在一起，页码与明确读取范围需要保留 |
| 结构化输出 | `tools/question_gen_tools.py` 通过各题型提交工具收集题目 | 整段 JSON 与逐字重抄公式耦合，单个引用不匹配会否决整个分析；应让服务器提供可引用的位置并逐条校验 |
| 原文引用 | 提交 `reference_text`，存溯源及页码；并非每条都做逐字子串验证 | 严格子串验证能阻挡伪造，但要求模型一边把 OCR 改成 LaTeX、一边逐字抄写本身冲突。位置引用保留原文，格式转换交给题干并独立复核 |
| 数量恢复 | 页级上限、零题再催一轮、工具提交即统计 | 一次分析失败就不再尝试；需要受限的修复反馈，正确处理部分成功，而非降低质量门槛凑数 |
| 正确性 | 提示词要求自检，普通题目提交主要检查数量及存储形态 | 保留额外独立审题，图片来源必须给审题上下文原页，不能只复核生成模型自己转录的公式 |

采用的是按页定位、结构化来源、局部恢复和先保证材料可读的经验。保持 Xinxin 自己的单主人鉴权、持久化任务、预算、取消与题目验收，不引入上游整个 Agent/数据库/前端，也不移植其不安全或不适合本地架构的运行方式。

这次复现还确认了三个需要长期保留的工程经验：

- 零入库要按阶段定位。这次主要失败发生在材料分析与引用校验，尚未产生候选题；只改出题提示词无法解决前置失败。
- 保留质量门槛，同时允许局部恢复。坏引用不应抹掉同批好证据，部分原页失败不应被成功页的摘要永久缓存；完整来源和答案复核仍不可跳过。
- 坐标也是协议。长行拆分后，即使 `L2` 这个字符串没变，其含义也可能改变；必须升级分析缓存版本。模型桩测试、真实本地 OCR、真实模型小样本与人工数学复算分别记录，不能相互替代。

外部能力依据：[DeepSeek 图片输入](https://api-docs.deepseek.com/guides/vision/)、[JSON 输出](https://api-docs.deepseek.com/guides/json_mode/)。图片读取仍可能出错；任何“模型已复核”均不代表数学正确性已获形式化证明。
