# 架构与实现

本文档说明 Xinxin 本地版的完整技术实现：技术栈、模块地图、数据模型、接口契约与各端形态。
适合想读懂代码、二次开发或安全评估的读者。产品层面的介绍见 [README](../README.md)。

## 1. 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 后端框架 | FastAPI（Python 3.12+） | 异步 HTTP、Pydantic 校验、OpenAPI 自动生成 |
| 数据层 | SQLite（WAL 模式） | 单文件事务型存储，19 张表；`BEGIN IMMEDIATE` + 有界重试解决并发写降级 |
| 任务引擎 | 自研 TaskManager | 持久化队列 + 单 worker + 事件流 + 预算控制 + 续接 |
| 模型接入 | OpenAI 兼容 Chat Completions | 默认 DeepSeek，可换任意兼容服务；流式解析带容错 |
| 检索 | BM25 Okapi + E5 稠密（int8 ONNX）+ 结构/标签 | 三通道加权融合，详见 [算法详解](算法详解.md) |
| 向量推理 | onnxruntime（CPU） | int8 量化模型，384 维，2 线程；无模型时降级词法通路 |
| 学习 | Shared LinUCB（证据门控） | 只有工具执行成功才更新策略 |
| 前端 | React 19 + TypeScript 5.9 + Vite 7 | 16 个页面，约 11000 行；无状态管理库，Hooks + Context |
| 可视化 | 自研 Canvas 渲染（技能球、农历） | 不依赖 three.js；设备像素比自适应 |
| 移动端 | Capacitor 8（Android） | 同一份前端打包 APK，预填后端地址 |
| PWA | vite-plugin-pwa + Workbox | prompt 型更新；API 不缓存 |
| 网关 | Caddy | 单端口反代 + 静态托管；生产禁用响应缓冲保证 SSE 实时性 |
| 桌面端 | PowerShell 5.1 + Edge 应用模式 | 无 Electron 依赖；WindowsJob 保证进程树随作业终止 |
| 公网（可选） | cloudflared 出站隧道 | 不需要公网 IP 与端口映射 |

代码规模：后端 31 个 Python 文件约 7900 行（含 SkillNet 子包 6 个文件 1445 行），
前端 31 个 TS/TSX 文件约 11000 行，桌面端 6 个脚本约 900 行。

## 2. 系统架构

```
┌─────────────────────────── 这台电脑 ────────────────────────────┐
│                                                                 │
│  手机浏览器 / PWA / APK        桌面浏览器      电脑软件端         │
│         │                          │              │              │
│         └──────────┬───────────────┘              │              │
│                    ▼                              ▼              │
│         Caddy 网关 :8080（唯一对外端口）      Edge 应用窗口        │
│              │                             （加载同一地址）       │
│      ┌───────┴────────┐                                         │
│      ▼                ▼                                         │
│  frontend :5180   backend :8010                                  │
│  Vite 预览        FastAPI + SQLite(WAL)                           │
│  （/api 反代）     ├── TaskManager   任务队列 / 预算 / 续接        │
│                    ├── ModelGateway  模型流式 + 用量统计           │
│                    ├── SkillRouter   三通道检索 + 重排 + 分流      │
│                    ├── SharedLinUCB  证据门控学习                  │
│                    ├── ToolExecutor  文件 / 命令 / 绘图 / 图片      │
│                    └── UploadGuard   上传前置校验                  │
│                                                                 │
│  backend/data/          账号·密钥·文件·记忆·任务·事件（SQLite）    │
│  backend/resources/     只读技能语料（1800+）与绘图模板            │
└─────────────────────────────────────────────────────────────────┘
```

三个角色都由 `Start-Xinxin-Local.ps1` 以「三角色进程管理」方式拉起，
清单写在 `.runtime/processes.json`；后端与前端只绑 `127.0.0.1`，
局域网唯一入口是 Caddy 的 `8080`。

### 为什么是单端口单进程

- **数据安全**：SQLite 单文件 + 单 writer，多进程争抢同一份库没有收益只有风险；
  任务引擎因此设计为「单进程单 worker」——这也让「任务有状态、可续接」变得简单。
- **网络收敛**：对外的认知面只有一个端口，防火墙规则、CORS 白名单、
  上传校验都只需在一处把关。
- **部署简单**：没有数据库服务、没有消息队列、没有容器编排；停服 = 复制一个目录。

## 4. 数据模型

单库 19 张表（`backend/app/store.py` 建表，全文可见）：

| 表 | 用途 |
| --- | --- |
| `owner` / `sessions` | 单主人账号与会话哈希 |
| `settings` | 键值配置：模型、密钥（加密）、技能策略、幂等标记 |
| `conversations` / `messages` | 会话与消息 |
| `runs` | 任务：状态、权限、预算、用量、`request_key`（唯一） |
| `events` | 事件流：`(run_id, seq)` 主键，SSE 与续传的基石 |
| `records` | 通用业务记录（内容、技能等按 kind 分） |
| `files` / `uploads` | 文件元数据与上传幂等签名 |
| `memories` / `schedules` | 记忆与定时任务 |
| `audit` | 审计流水 |
| `run_context` / `run_plan` / `message_runs` / `conversation_options` | 任务上下文、计划、消息关联、档位 |

设计要点：

- **事件表是唯一事实源**：任务过程不依赖内存；重启后读 `events` 即可重建全部进度
- **`request_key` 唯一索引**：重复提交返回同一个 `run_id`，执行不重复
- **WAL + `BEGIN IMMEDIATE`**：写连接先抢写锁再执行业务，失败有界重试；
  避免「连接被降级为只读却返回 READONLY 而非 BUSY」的静默故障
- 停服后复制 `backend/data/` 即完整备份；`vault.key` 丢失则加密凭据不可恢复

## 5. 接口契约

- 全部业务接口在 `/api/v1/` 下，健康检查在 `/health`
- 75 个端点按域分组：auth / conversations / runs / events(SSE) / files / records /
  skills / schedules / settings / network
- 认证：`Authorization: Bearer <session>`；单主人，CORS 精确来源白名单
- 错误响应统一 `{detail}`，422 会脱敏后再回给前端（不回显输入值与未知字段名）
- 流式：`GET /api/v1/runs/{id}/events?after=N`，断线重连带 `Last-Event-ID`，
  服务端按游标补发，不重不漏

### 事件类型

| kind | 含义 |
| --- | --- |
| `queued` / `started` | 任务入队 / 开始执行 |
| `skills` | 本轮技能选择：decision、confidence、components、selection、candidates |
| `usage` | 累计用量（调用次数、令牌） |
| `tool.started` / `tool.completed` | 工具开始 / 完成（含 ok 与结果摘要） |
| `delta` / `progress` | 回复增量 / 过程说明（分开记录，断流草稿不污染历史） |
| `finished` | 终态：结果、错误、用量一起落库 |

## 6. 前端架构

```
src/
├── main.tsx            入口：ErrorBoundary → Router → Providers → App
├── App.tsx             外壳：认证态、侧栏、顶栏、搜索、路由（含错误边界）
├── api.ts              HTTP 封装 + SSE（游标重连、坏事件跳过、幂等 key）
├── safeJson.ts         安全 JSON 解析（脏数据兜底）
├── ErrorBoundary.tsx   渲染异常兜底页
├── ui.tsx              Dialog / Loading / Toast / useResource 等基础件
├── Uploads.tsx         上传 Context（X-Upload-ID 幂等 + 进度）
├── editor.tsx          tiptap 富文本编辑器（私有图片节点）
├── runText.ts / runSubmission.ts   回复拼装 / 任务提交（向后端能力协商）
├── conversationLocation.ts / privateImages.ts
└── pages/              16 个页面：Dashboard / Agent / Tasks / Files / Servers /
                        Skills / Content / Tools / Memories / Schedules / Settings
                        + SkillSphere（Canvas 技能球）/ GalleryExplorer 等
```

前端没有引入 Redux/MobX 一类状态库：会话态在页面级 Hooks，跨页状态走 Context
（Toast、Upload），服务端状态一律现取。样式是 6 个分层 CSS 文件
（styles / workspace / agent / capabilities / polish + PWA），用 CSS 变量做主题。

## 7. 各端形态如何实现

| 形态 | 实现 |
| --- | --- |
| 电脑软件端 | `desktop/Xinxin-Desktop.ps1` 拉起三服务 → 就绪后以 Edge 应用模式
（`--app=`）开无地址栏窗口；互斥锁保证单实例；端口占用等错误弹出本地诊断页。
详见 [电脑端.md](电脑端.md) |
| 桌面浏览器 | 直接访问 `127.0.0.1:5180` 或局域网 `:8080` |
| 手机浏览器 | Caddy 单端口 + 响应式布局 + PWA（可添加到主屏幕） |
| Android APK | Capacitor 打包同一份前端，`build-android.ps1` 预填后端地址 |
| 公网访问（可选） | cloudflared 出站隧道 → Caddy；地址写入 `.runtime/public-url.txt`，
设置页「连接地址」可直接复制。详见 [远程访问.md](远程访问.md) |
